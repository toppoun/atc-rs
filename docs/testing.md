# テストと Watch

`atc` は、公式サンプルの単発テスト、任意の入力の実行、ソース保存時の自動テストに対応しています。

## まず1問テストする

Contest 画面で問題 A を選び、`r` を押します。コマンドから実行する場合は、Contest フォルダで次を実行します。

```bash
atc test A
```

C++ は1回 compile してから各ケースを実行し、Python は各ケースを直接実行します。テストが失敗した場合、コマンドの終了 status も失敗になります。

## サンプルテスト

Contest フォルダで:

```bash
atc test A
```

ワークスペースのルートからコンテストを指定する場合:

```bash
atc test A -c abc466
```

言語を明示する場合:

```bash
atc test A -l cpp
atc test A -l python
```

`-l` を省略すると、設定の `[defaults].language`、その次に組み込みの `cpp` が使われます。

指定された言語のソースが存在しない場合、別の言語のソースへ自動で切り替えることはありません。

問題名は大文字・小文字を区別せずに照合します。どの言語も Contest フォルダを作業フォルダとして実行します。

公式サンプルも保存済み Stress ケースもない場合は `No Samples` と表示し、コンパイルや候補プログラムの実行は行いません。

保存された公式サンプルの件数が Contest の記録と一致しない場合、テストは実行前にエラーになります。`atc refresh` で公式サンプルを取り直してください。User Input と保存済み Stress ケースは公式サンプルの件数に含まれません。

## C++ Debug

C++ では `--debug` を利用できます。

```bash
atc test A --debug
```

TUI では `d` で Debug を切り替えます。コマンドから実行する Stress Test でも `--debug` を指定できます。

Debug ビルドでは、通常の `cpp_flags` に `-DLOCAL`、`-D_GLIBCXX_ASSERTIONS`、組み込み `debug.hpp` の include path を追加します。ヘッダーはユーザーの cache ディレクトリへ展開されます。

解答コードで AtCoder Library の `<atcoder/modint>` または `<atcoder/all>` を読み込むと、`debug(x)` で `static_modint` や `dynamic_modint` の `val()` を表示できます。例えば `atcoder::modint998244353` に `-1` を代入した変数は `998244352` と表示されます。`std::vector` などに入れた値も表示できます。

GNU libstdc++ では `std::vector::operator[]` などの範囲外アクセスを検出できます。アサーションで異常終了したケースは `RE` になり、標準エラー出力は CLI の `stderr` 欄や TUI のケース詳細に表示されます。macOS 標準の libc++ では、範囲チェックは使用中のツールチェーンの設定に従います。

Python では `--debug` は使用できません。

## 判定方法

出力比較では次を許容します。

- CRLF / LF の違い
- 各行末の空白の違い
- 最終改行の有無

一方、次は区別されます。

- 行頭の空白
- 行の途中の空白
- 空行の構造

候補プログラムが `stderr` を出していても、`stdout` が正しければそれだけで不正解にはなりません。必要に応じて `stderr` は結果に表示されます。

主な結果:

- Accepted
- Wrong Answer
- Runtime Error
- Time Limit Exceeded
- Compile Error
- Compile Timeout

## User Input

公式サンプル以外の入力を試す場合は、Contest 画面の `Samples` pane で `+ New Input` をクリックします。

1. stdin を入力する
2. `Ctrl+S` または `[Save]` で保存する
3. `[Run]` でその入力だけを実行する

保存後は `[Edit]` で変更できます。編集中に `Esc` または `[Cancel]` を選ぶと、変更を保存せずに戻ります。編集中の `[Run]` は、保存前の現在の内容を実行します。

User Input には expected output がないため、AC / WA は判定しません。終了状態、stdout、stderr を確認してください。また、`r` や `atc test` の一括テストには含まれません。

保存先は次のとおりです。

```text
.atc/user-inputs/<problem>/<id>.in
```

削除するには `×` をクリックし、確認のためもう一度 `×` をクリックします。保存した入力ファイル自体が削除されます。

外部エディタでファイルを変更した場合は、問題を開いたとき、編集を始めたとき、または実行するときに読み直します。TUI で編集中の内容は、外部の変更で上書きされません。

## 保存済み Stress ケース

Stress Test で反例が保存されている場合、公式サンプルの後に回帰テストとして実行されます。

つまり、一度見つけた反例は次回以降の:

```bash
atc test A
```

でも確認できます。

保存済みの反例を読み込めない場合はエラーになり、その問題を成功扱いにしません。反例のファイルは自動で変更されません。表示されたファイルを確認し、必要ならバックアップを取ってから復旧してください。

以前の形式で保存した一部の Runtime Error / Time Limit Exceeded 反例は、期待出力がないため再実行できません。後からファイルが欠けた可能性も区別できないので、公式サンプルをテストしても反例は未検証と表示し、AC 件数には含めず、CLIは失敗の終了コードを返します。復旧手順は [ストレステスト](stress.md) を参照してください。

詳しくは [ストレステスト](stress.md) を参照してください。

## Watch

TUI で監視する場合:

```bash
atc watch
```

テキスト出力だけで監視する場合:

```bash
atc watch --plain
```

ワークスペースのルートからコンテストを指定する場合:

```bash
atc watch -c abc466
atc watch -c abc466 --plain
```

Watch は Contest フォルダ直下の問題ソース（`A.cpp`、`A.py` など）が変更されたときにテストします。Stress Helper やサブフォルダ内のファイルは、通常のソース変更として扱いません。

保存済みの Stress ケースを読み込めず、対象の問題を特定できる場合は、その問題のテストを止めて確認先を表示します。他の問題の監視は続きます。監視中にコンテストの復旧が必要になった場合は、表示された場所を確認してください。

### 起動直後の挙動

Watch は**起動時に全問題を一度テストする方式ではありません**。

`watch --plain` でコンテストの更新中や復旧待ちにソースを保存すると、その回のテストはエラーになります。監視は続くので、更新や復旧を終えてからソースを保存すると、データを再確認してテストします。

起動後にソースファイルが変更・保存されたタイミングでテストが走ります。

今すぐ実行したい場合は、TUI で `r` を押すか、別途 `atc test` を実行してください。

### Cross-Contest Watch

Cross-Contest Watch を有効にすると、Workspace の Contest TUI を開いている間、同じ Workspace 内の管理対象 Contest のソースを監視します。保存すると、その問題のサンプルテストを受け付け、最後に受け付けた保存先の Contest・問題・言語を表示します。デフォルトは無効です。[Settings または Global Config で有効化](configuration.md#cross-contest-watch)できます。Standalone と `atc watch --plain` では、開いた Contest のソースを監視します。

- 非表示の Contest のテストも共通のキューに入り、同時に実行するテストは1件です。新しい保存を優先し、中断したサンプルテストがまだ有効なら、あとで最初から実行します。キューの消化や実行結果によって表示が移ることはありません。
- User Input の編集や提出確認などのモーダル中は、表示の切り替えを保留します。その間も実行と結果更新は続きます。操作が終わった時点で、最後の保存先が有効なら表示します。手動で Contest の切り替えを確定した場合、それまでに受け付けた自動切り替え候補は取り消されます。
- 非表示の Contest の C++ は Debug OFF で自動実行します。切り替え後の Debug 設定が実行時と異なると、ヘッダーに次回とその実行の値を表示します。
- 各問題の最新結果をメモリに保持します。有効時の完了結果は Workspace 全体で最大64問題、推計64 MiBです。上限を超えると古い完了結果から取り除きます。待機中と実行中の状態はこの上限の対象外です。User Input の結果は1問あたり最新8件まで保持します。無効時と Standalone では、開いている Contest の各問題と各 User Input の最新結果を保持します。Refresh などで管理データが更新された Contest は、古い結果を破棄します。Workspace Home に戻るか終了すると、監視と実行を停止し、保持していた結果を破棄します。

監視対象の Contest が増えると、システム資源の使用量も増えることがあります。Git checkout など外部ツールによるソース更新も保存と同様に扱われる場合があります。OS がファイルの権限などの属性変更だけを通知した場合は、保存によるテストや自動切り替えは起きません。通知が欠けた場合は最終状態を再照合し、見つかった変更をテストします。再照合で見つかった変更では表示を切り替えません。すべての通知や変更順序を復元できる保証はありません。

監視中のソース再照合は、手動の Contest 切り替えや通常の保存通知を合間に処理します。Contest の配置や管理データを確認している間は、切り替えに時間がかかることがあります。

一部の登録に失敗した場合は、TUI の状態行を確認してください。利用できる監視対象では監視を続けます。

## タイムアウト

デフォルト:

```text
実行:       2.0 秒
コンパイル: 10.0 秒
```

変更方法:

```toml
[runner]
timeout_seconds = 3.0
compile_timeout_seconds = 15.0
```

詳しくは [設定](configuration.md) を参照してください。

## 出力サイズ

各プロセスの `stdout` / `stderr` はそれぞれ最大 8 MiB まで取得します。

候補プログラムの出力が上限を超えて切り詰められた場合、その出力を Accepted として扱うことはありません。
