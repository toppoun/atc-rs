# Cross-Contest Watch Phase 8B-1 Windows 実装と検証

2026-11-26。比較元は Phase 8A の `2062286`。Windows 11 25H2、大小文字を区別しない NTFS、Ryzen 7 9800X3D、Rust 1.97.1、notify 8.2.0 と `notify-types` 2.3.1。前回の計測条件と検証方法は [Phase 8B Windows 起動調査](cross-contest-watch-phase8b-windows.md) を参照。

## 測定方法

実装前後の通常リリース版を同じ Windows の ConPTY 120×40 で実行した。合成 Workspace は各 Contest が2問、正規の既存ソース3本、未作成の候補1本。表示・切り替えの2 Contest には前回と同じサンプルと User Input を置いた。Enter 確定から対象画面を観測するまでを測り、通常切り替えと Home からの再 Open を同じ試行に含めた。

新規データは各条件3回、ウォームは5回。新規データは新しいプロセスと別々の合成 Workspace を使った。ウォームは一度 ON で開いた同じ Workspace を再利用し、比較元と実装後の実行順を交互にした。OS 全体のキャッシュは操作していない。

処理時間と I/O 回数は一時コピーへの同じ計測点で採取した。ウォーム各条件3回と、1,000 件の新規データ各条件3回を比較した。CPU 時間は `GetProcessTimes`、Private Bytes と Working Set はプロセスメモリ情報、ハンドルとスレッドは Windows API で採取した。回数はアプリケーションから呼び出した境界で、Win32 や依存ライブラリ内の呼び出しまでは含めない。

## macOS への適用範囲

診断で検証したマニフェストと Recovery 状態の引き渡し、探索時の属性再利用、既存世代の配置・マニフェスト照合は共通コードにある。初期索引の前処理と定期照合の I/O が減る見込み。macOS の FSEvents 一括登録と Ready 後の回収、Windows の Ready 前の照合、および稼働中の照合の処理単位は既存の経路を使う。

macOS 上の実行・計測は未実施。Windows からのオフラインのクロスチェックは notify 9.0.0 のキャッシュがなく、コンパイル前に停止した。

## Phase 8B の判定

今回の範囲は完了とする。ウォーム起動で約10〜14%、1,000件の定期配置照合で約18%短縮し、Windows の既存挙動の回帰は再現しなかった。通常切り替えと保存受付の待ち時間は同程度だった。案Bのハンドル共有、案Cの遅延初期化、案Dの Ready 後への移行、案Eの並列化、案Fのバックグラウンド初期化は、今回の数値から追加実装が必要とは判断しない。

新規データの1,000件を約4秒より短くする目標が必要になった場合は、最初の安全なファイルオープン待ちをストレージ・OS キャッシュ・ファイルシステムフィルターに分けて測る。その結果で案Eの必要性を判断する。基準指紋と登録後指紋の境界、所有権と実体の確認、通常通知の順序と回収の条件は、以後の比較でも検証する。

OS 再起動直後、他の NTFS 設定やストレージ、macOS 実機、自然な通知飽和、カーネル全体の I/O 記録は未検証。一時ディレクトリ `target/phase8b1` に外部観測の `release.jsonl`、処理別の `start-*.csv` と `run-*.csv`、定期照合・保存受付・リソースの `runtime.jsonl`、通常権限の全テストログと再現スクリプトを保存した。
