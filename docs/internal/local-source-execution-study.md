# ローカル実行における主ソースの整合性

2026-11-26、Phase 7C の設計・検証記録。対象は `992be35`。主ソースのスナップショット化は、CLI、Plain Watch、TUI、Stress、ランナー設定にまたがる独立した改善課題として保留した。Phase 7C-1〜7C-4 の実装は行っていない。現行の契約は [INVARIANTS.md](INVARIANTS.md) を参照。

## 現行経路

- [Sample Test](../../src/commands/test.rs) に CLI `atc test` と [Plain Watch](../../src/commands/watch.rs) が合流する。サンプルと反例は読み込んで保持する。C++ はパスを渡して一度コンパイルし、Python はケースごとにパスを渡して起動する。
- Workspace TUI と Standalone は [AttemptExecutor](../../src/commands/attempt_executor.rs) を使う。ON・OFF とも `RunContext` が所有権、task、管理メタデータを検証する。ON では正規ソースから指紋も取得するが、そのバイト列は [ランナー](../../src/runner.rs) に渡さない。[User Input](../../src/commands/user_input_run.rs) は入力のバイト列を保持し、主ソースは起動時にパスで指定する。
- [Stress](../../src/stress.rs) は候補 C++ を一度コンパイルする。候補 Python、generator、reference はケースごとに起動し、パスを開き直す。反例は seed、入力、期待値、実際の出力を保存する。現行形式に3役のソースの同一性を記録する欄はない。
- [ContestTaskSnapshot](../../src/workspace.rs) はディレクトリ実体、復旧状態、マニフェストを保持する。[RunGeneration](../../src/tui/message.rs) は実行要求と結果の所属および User Input の開始ゲートを管理する。主ソースのバイト列はどちらにも含まれない。
- [SubmissionHub](../../src/tui/submission.rs) は確認時点で取得した内容を [PreparedSubmit](../../src/commands/submit.rs) に保持する。ワーカーに所有済みデータを渡す設計は参考になる。現行の提出ソース読み込みは `fs::read_to_string` である。ローカル実行で安全な読み込みを組み立てる際は [safe_file](../../src/safe_file.rs) の `read_stable_regular_file_at` と、開いた Contest ディレクトリに対する相対アクセスが再利用候補になる。提出の責務と API は独立させる。

検証時に観測したファイルと、子プロセスが元パスを開く時点のファイルが一致する保証はない。この境界は Cross-Contest Watch 以前からある。ON では表示していない Contest の保存でも実行を開始できるため、対話中に実行対象になりうる範囲が広がる。

## 再現・検証記録

一時的な合成 Workspace、ローカルの Global Config、無害なテストプログラムを使用した。macOS 26.6.2 arm64、Apple Clang 17、Homebrew GCC 16.1、CPython 3.9.6 と 3.14.6 で確認した。Windows での実機検証は未実施。

| 条件 | 確認した結果 |
| --- | --- |
| Python の3ケース中、1ケース目の開始を確認して通常の編集を保存する | 現行リリースの `atc test` は旧版、新版、新版の順に実行。Global Config の ON・OFF の両方で再現。 |
| Stress の開始後に候補または補助スクリプトを保存する | 現行リリースでは候補 C++ は既存バイナリを使い、候補 Python、generator、reference は各プロセスの起動時点の内容を使用。reference の編集後に保存した反例は、保存済み入力と期待値で再実行できた。 |
| 取得済みの主ソースに通常ファイルへの置換、同一実体の上書き、削除・再作成を行う | プロトタイプは取得済みバイト列を維持。次の物理 attempt として取得し直すと新版を使用。 |
| リンクが置かれたソースを取得する | プロトタイプはリンクを拒否。取得後の元パス変更はコピーに影響しない。 |
| 読み込み中に同じ実体・同じ長さの内容を更新する、または同じ内容の別実体に置き換える | プロトタイプは読み込み前後の照合で変更を検出し、取得を中断。 |
| 取得後に Contest ディレクトリを移動する | プロトタイプはコピーを保持。元の cwd がなくなった場合は子プロセスの起動に失敗する。 |
| 連続保存、Refresh、世代失効、途中終了 | 現行リリースの TUI は ON・OFF・Standalone で連続保存後に最新要求が完了。既存テストで Refresh・世代失効・join 後の再キューを確認。プロトタイプでは子プロセスの終了確認後にコピーを解放。スナップショットと本番 TUI の統合は未検証。 |

性能の参考値として、通常の 4 KiB と大きな 4 MiB の取得はそれぞれ中央値 29 µs、226 µs。一時ファイル生成は 91 µs、670 µs。Python の通常サイズで6ケースは 115 → 124 ms、4 MiB のピーク RSS は 14.5 → 23.1 MiB だった。関連する現行テストは106件成功、失敗0、既存 ignored 12。本番コードに組み込んだ応答時間は未計測。

## 設計候補

| 方式 | 評価 |
| --- | --- |
| 検証済みハンドルから attempt 専用の一時ファイルにコピー | 推奨。元ファイルの変更から取得済みバイト列を切り離せる。C++ と Python はパスを受け取れるため、共通の取得・解放と、言語別の引数・診断の補正に分けられる。 |
| 開いた FD・ハンドルを渡す | macOS の `/dev/fd` 経由で Clang、GCC、Python の単純な実行を確認。同じ実体への上書きは引き続き見える。Windows の共有モードを使う場合はエディタとの互換性、ハンドル継承、一般のコンパイラが参照できる名前を検討する必要がある。 |
| ソースを stdin で渡す | C++ はコンパイル時と実行時で stdin を分離できるが、include とパスの補正が必要で、試験では GCC の `__BASE_FILE__` に差が出た。Python の `python -` はサンプル入力に使う stdin を消費する。 |

取得単位は物理 attempt とする。世代・task・所有権が有効なことを確認した後、最初の子プロセスを起動する前に取得する。安全に開いた同じハンドルから読み、読み込み前後と再オープン時に実体・サイズ・更新時刻を照合する。取得後に所有権と Cancellation を再確認する。監視範囲の外に専用領域を作り、Unix の所有者限定権限と Windows の DACL を確認し、no-clobber で作成する。子プロセスとパイプ処理の終了を確認してから解放する。

Samples を同じ `RunId` で再キューした場合は、新しい物理 attempt で取り直し、ケースを先頭から実行する。元のコピーを再利用すると、再キューから実行までに編集したソースを旧版で動かすことになる。スナップショットはキューや結果ストアに保持しない。Stress は候補、generator、reference をいずれも attempt 開始時に固定する候補とする。

保証は、取得した主ソースの内容を同じ attempt の各起動で使う範囲に限る。複数ファイルの取得を同時点とみなすことはできない。ヘッダー、import、cwd、実行中の任意のファイルアクセス、観測に現れない書き込み、同一ユーザー権限による一時領域への干渉、実行環境全体の再現性は別の課題となる。

## 本実装前に解決する互換性

- C++ は元のディレクトリを引用 include の探索に含める必要がある。既存の `-iquote` の後ろに追加すると別のヘッダーが選ばれた。GCC の `-I-` とユーザー指定のパスマップでも差を確認した。`__FILE__` / `__BASE_FILE__` と診断パスは別々に検証する。診断のパス補正で VS Code が元ファイルの行・列へ移動できた。Clang VFS は元パスが存在する条件で有効だが、元ファイルを削除するとドライバが入力を拒否した。ACL、`atc/debug.hpp`、`LOCAL`、cwd を含む通常の構成は両コンパイラで確認した。
- Python は同名ランチャーで `sys.path`、`__file__`、`sys.argv`、cwd、stdin を維持できた。標準の例外表示に任せた初版は、旧版のコードを実行しても traceback の行本文を新版から読んだ。スナップショットの行本文を渡す処理が必要となる。設定済み Python ラッパーが元ファイルの絶対パスを要求する場合は互換性がなく、`sys.orig_argv` や起動時の監査イベントにも差が残る。
- Windows の GCC と CPython、NTFS の reparse point・共有モード・DACL、Unicode・長いパス、終了後の一時資源解放を実機で検証する。未対応の設定で検証済みコピーから元パス読み込みへ暗黙に戻ると整合性の保証が失われる。設定の互換性の範囲と、明示するエラーを先に決める。

着手時は、安全な取得・解放の共通部、C++／Python のランナーと Sample 経路、User Input と Stress の順に検証する。所有権、世代、Cancellation / Join、最新要求優先、FIFO、有効な Samples のみの再キューを各段階の確認条件とする。
