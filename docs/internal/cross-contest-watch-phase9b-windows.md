## 公開前修正

- Contest の診断とマニフェストのスナップショット再読込を同じ 16 MiB 上限付き処理にした。開いたハンドルの属性で超過を早期に拒否し、サイズが増加した場合も上限と超過判定用の 1 バイトまでで読む。no-follow、通常ファイル・reparse point の判定、ファイル実体、Contest ディレクトリ実体、Recovery 状態、所有権の検査を維持した。ポーリングに渡す属性は内容と同じファイルハンドルから得る。[安全な読み込み](../../src/safe_file.rs)・[診断](../../src/workspace/diagnosis.rs)・[スナップショット](../../src/workspace.rs)
- 上限超過の `InvalidData` は、他の不正なマニフェストと同じ経路で処理する。登録前は診断・世代登録を拒否し、稼働中の再照合は対象世代を失効してキューと結果を外す。保存受付と物理 attempt 前も再検証する。正常なマニフェストへ戻すと新世代を登録し、他 Contest の有効世代はその間も保持する。[監視ループ](../../src/commands/workspace_watch.rs)・[物理実行](../../src/commands/attempt_executor.rs)

合成 Workspace の登録済み非表示 Contest のマニフェストを 64 MiB の通常ファイルに置換した。リリース版の同一手順で、置換前と置換後 2.5 秒間の最大観測値を比較した。単位は MiB。

| --- | ---: | ---: | ---: |
| Phase 8B-1 | 3.48 → 67.62 | 22.75 → 84.57 | 22.75 → 86.80 |
| Phase 9B | 3.45 → 3.45 | 12.38 → 12.49 | 12.38 → 12.49 |

修正後は今回の採取間隔で 64 MiB 相当の増加がなく、不正マニフェストの保存では子プロセスが起動しなかった。別 Contest と復元後の Contest は各 1 回実行し、画面で `1/1 AC` を確認した。追加した回帰テストは、16 MiB の直前・同値・超過、属性取得と読み込み開始後にサイズが増えた通常ファイル、64 MiB 置換時の旧世代失効、健全な世代での実行、復元後の新世代と実行を確認する。増加試験では超過判定用の 1 バイトで読み取りが止まったことをファイル位置で確認した。

## Contest 追加直後の保存

500 件が稼働中の Workspace に、別の場所で作成した 180 件を配置ルールの更新で追加した。計測版の監視スレッドから対象 1 件の正規ソースを実際に書き換え、変更開始・終了、対象の登録、回収、ネイティブコールバック、RunScheduler の受付、Python の起動回数、ConPTY の表示を記録した。各時点 3 試行。表の受付件数は各試行で同じ。登録処理中の注入点は個別の `register` の入口で、対象について最初の Win32 監視要求を発行する前。

| 保存時点 | 受信した通常通知 | 通常受付 | 回収受付 | 実行 | 自動切り替え |
| --- | ---: | ---: | ---: | ---: | --- |
| 初回指紋取得前 | 0 | 0 | 0 | 0 | なし |
| 基準指紋取得後、監視登録前 | 0 | 0 | 1 | 1 | なし |
| 個別の監視登録処理中、バックエンドに渡す前 | 0 | 0 | 1 | 1 | なし |
| 対象の監視登録完了直後 | 3 | 1 | 0 | 1 | あり |
| 登録後の再照合中、対象ソースの読み取り直前 | 3 | 1 | 0 | 1 | あり |
| 再照合完了後 | 3 | 1 | 0 | 1 | あり |

初回指紋取得前の保存は基準に取り込まれ、変更としては観測されない。取得後から監視開始前の差分は照合で回収した。回収の対象は内容やファイル実体など、指紋に差が残る変更。登録後に届いた `Modify(Any)` は固定窓ごとに通常の保存 1 件となった。通常通知を遅らせる追加の 1 試行では、Atomic Save のコールバックを保留し、約 13.8 秒後の定期照合で 1 回実行した。画面は維持し、保留した通知を再投入しても実行・画面遷移は増えなかった。本来受付できる差分の未回収は今回の条件で観測せず、macOS の単発事例の原因は未確定。

## 残件と公開判断

**Phase 9C へ進行可。** Windows の通常権限で公開を妨げる問題は確認しなかった。コードレビューで確認した Windows notify の下位障害の見え方と、macOS で一度観測した追加直後の未受付は、再現条件を特定できた場合の調査項目とする。

- macOS では今回変えた共通コードの 16 MiB 境界、読み込み中の増加、64 MiB 置換時のメモリと世代失効、他 Contest の継続、復元後の FSEvents 受付を再検証する。Phase 9A の実機結果は今回の修正前。
- Linux 実機、NTFS の大小文字を区別する設定、ネットワークファイルシステム、OS 再起動直後のコールド性能、自然な通知飽和、複数時間の連続運転は未検証。故障注入の結果は実際の OS キュー飽和の証拠にはならない。Windows で個別の `ReadDirectoryChangesW` API 自体の失敗は今回注入していない。
- 16 MiB の検証対象は診断と管理タスクのスナップショット読み込み。手動 Open の準備には、健全性確認後に `load_metadata_unchecked` で表示用マニフェストを再読込する別経路がある。その間にファイルを差し替えるケースへの上限適用は、将来の確認項目とする。[画面準備](../../src/commands/watch_tui.rs)・[表示用の読み込み](../../src/workspace.rs)
- 実 AtCoder への通信や提出は行っていない。Source Snapshot、起動の追加最適化、並列 I/O、永続キャッシュ、新機能は今回の対象外。

計測スクリプトと生ログはローカルの `target/phase9b` に保存した。通常リリース版と計測版を分けてビルドし、計測点と障害注入コードは作業用コピーに置いた。
