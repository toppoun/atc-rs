## 1. Problem identity

- **対象となる操作** — AtCoder の問題一覧取得、Contest メタデータの保存・読込、Test・Stress・Submit の問題選択。
- **保証する動作** — Contest ID はコンテスト、`index` は表示・ローカルパスの問題ラベル、`task_id` は AtCoder 上の問題を識別する。問題一覧ではラベルとタイトルのリンクが一致し、指定 Contest 配下の有効な task ID を指すことを確認する。確定したメタデータは `https://atcoder.jp/contests/<contest-id>/tasks/<task-id>` と文字列で一致する URL を持つ。CLI のラベル検索は ASCII 大小文字を区別せず、明示した Contest ID はメタデータと完全一致で照合する。
- **拒否・失敗・中断時の動作** — 空の問題一覧、重複 task ID、安全なパス要素にならない ID・ラベル、ASCII 大小文字だけが異なるラベル、異なる Contest・task を指す URL を通常のメタデータとして受理しない。Test・Stress は開始時に現在のラベルと task ID の組を確認し、Submit は POST 直前にも Contest と task の対応を確認する。
- **保証しない範囲と例外** — task ID を Contest ID とラベルから合成しない。安全な形式の URL と task ID の不一致や重複 task ID は、修復用の検査では条件付きで扱う。所有の判定は[契約 4](#4-contest--stress-recovery)を参照。
- **関連する本番実装** — [src/atcoder.rs](../../src/atcoder.rs) の `parse_contest`、[src/workspace.rs](../../src/workspace.rs) の `validate_contest_paths`、`validate_contest_identity`、`ContestTaskSnapshot::problem`、[src/commands/test.rs](../../src/commands/test.rs) の `find_problem`、[src/commands/submit.rs](../../src/commands/submit.rs) の `verified_post_gate`。
- **関連する回帰テスト** — [src/atcoder.rs](../../src/atcoder.rs) の `parses_contest_from_tasks_fixture`、`malformed_tasks_fixture_is_a_parse_error`。[src/workspace.rs](../../src/workspace.rs) の `loaded_metadata_rejects_duplicate_task_ids_across_indices`、`contest_paths_reject_case_insensitive_problem_index_collisions`、`metadata_health_distinguishes_repairable_task_url_mismatch_from_unsafe_url`、`test_samples_use_the_live_count_and_reject_a_changed_task_binding`。[src/commands/submit.rs](../../src/commands/submit.rs) の `adt_request_uses_the_stable_metadata_task_id`、`metadata_change_at_post_gate_prevents_mock_send`。
- **未検証事項・プラットフォーム依存事項** — 未確認の問題一覧 HTML 形式への対応。ASCII 大小文字の検査はメタデータの規則であり、実際のパスの同一性は[契約 9](#9-windows--macos-filesystem-differences)を参照。

## 2. Verdict integrity

- **対象となる操作** — CLI の `atc test`・`atc stress`、Watch / TUI の Sample Test。
- **保証する動作** — 現在のメタデータの `sample_count` と、1 から連番の UTF-8 入出力ペアを照合する。取得時も、サンプル見出しがないだけでは 0 件と判断しない。公式サンプルを番号順に実行し、再実行可能な保存反例を最後に追加する。実行が正常終了し、stdout が UTF-8 で切り詰められておらず、比較が一致した場合に AC とする。比較は CRLF、行末空白、末尾改行の有無を吸収する。単発 CLI は失敗イベントを累積するので、後続の AC が先行の失敗を消すことはない。
- **拒否・失敗・中断時の動作** — 件数やペアの欠落、破損した保存反例などは実行前にエラーにする。タイムアウトは TLE、異常終了は RE、正常終了でも不正・切り詰め済みの stdout は WA。Stress の生成器・参照解の実行や stdout が不正な場合は比較を成立させずエラーにする。単発 CLI は判定失敗、コンパイル失敗、Test での反例の未検証スキップ、Stress の中断、操作エラーで非ゼロ終了する。
- **保証しない範囲と例外** — 公式件数が 0 で再実行できる反例もなければ、コンパイルや解答の実行をせず `NoSamples` を通知する。このイベント自体は CLI の失敗に数えない。未検証スキップを伴う場合は非ゼロ。TUI では `NoSamples` が終端状態となる。判定をプロセス終了コードに変換する規則は単発 CLI に適用する。
- **関連する本番実装** — [src/atcoder.rs](../../src/atcoder.rs) の `parse_samples`、[src/workspace.rs](../../src/workspace.rs) の `load_test_samples`、[src/commands/test.rs](../../src/commands/test.rs) の `test_problem_with_debug_header_and_cancel`、`run_test_cases`、`judge_case`、[src/comparator.rs](../../src/comparator.rs) の `compare`、[src/stress.rs](../../src/stress.rs) の `run`、`candidate_failure_kind`、[src/main.rs](../../src/main.rs) の `run_verdict_command`。
- **関連する回帰テスト** — [src/atcoder.rs](../../src/atcoder.rs) の `statement_without_samples_or_positive_zero_evidence_is_a_parse_error`。[tests/verdict_exit_cli.rs](../../tests/verdict_exit_cli.rs) の `missing_one_official_sample_fails_before_running_solution`、`valid_saved_stress_case_runs_after_official_sample`、`a_later_ac_does_not_erase_an_earlier_failed_verdict`、`runtime_error_exits_nonzero`、`runtime_timeout_exits_nonzero`、`stress_counterexample_exits_nonzero_after_reporting_and_saving`。[src/commands/tests.rs](../../src/commands/tests.rs) の `invalid_utf8_candidate_output_cannot_be_accepted_as_replacement_text`、`truncated_candidate_output_cannot_be_accepted_as_displayed_prefix`、`no_samples_is_reported_without_starting_a_runner`。[src/tui/app.rs](../../src/tui/app.rs) の `no_samples_is_terminal_and_is_not_overwritten_by_completed`。
- **未検証事項・プラットフォーム依存事項** — AtCoder の本番ジャッジとの同値性は未確認。ここでの AC はローカルの実行と比較に対する判定。

## 3. Stress case ownership

- **対象となる操作** — 保存反例の Sample Test への追加、Stress 開始時の検査、新しい反例の保存。
- **保証する動作** — v1/v2 は Contest ID と問題ラベル（ASCII 大小文字を区別しない）で照合する。v3 は有効な task ID を必須とし、現在の task ID と完全一致させる。保存は v3。再実行には `failed.in` と `expected.out` を用いる。Stress 開始時に Contest ディレクトリの同一性・メタデータ・復旧状態を記録し、反例の保存中は問題単位の排他ロックと Contest 更新の共有ロックを使って、配置前などに再検証する。有限回の正常完了も報告前に Contest を再検証する。
- **拒否・失敗・中断時の動作** — 所有不一致、不正なバージョンや seed 情報、必須データの欠損、未解決の復旧状態をエラーにする。Contest の task 変更や中断した更新を検出したら反例の配置を拒否する。v1 の RE/TLE で `expected.out` がない場合、Sample Test は未検証と報告し、ケース数・AC 数に含めない。v2/v3 および v1 の WA では同ファイルが必須。
- **保証しない範囲と例外** — v1/v2 の task ID は不明で、ラベルの再割り当てを識別できない。v1 RE/TLE の期待出力欠損は当時の正常な保存と後からの欠損を区別できない。保存済みの RE/TLE でも期待出力が有効なら現在の解答を再判定する。取消を確定できるのは保存処理の切替前までで、切替開始後は復旧処理を含めて進める。
- **関連する本番実装** — [src/stress.rs](../../src/stress.rs) の `run`、`valid_failure_metadata`、`read_saved_case_snapshot`、`validate_failure_generation`、`persist_failure_inner`、[src/workspace.rs](../../src/workspace.rs) の `ContestTaskSnapshot::capture`、`ContestTaskSnapshot::revalidate`。
- **関連する回帰テスト** — [tests/verdict_exit_cli.rs](../../tests/verdict_exit_cli.rs) の `rc13_legacy_stress_cases_replay_and_v3_checks_the_task`、`historical_and_damaged_v1_runtime_failures_are_indistinguishable_on_disk`、`ambiguous_v1_stress_case_does_not_hide_an_official_sample_wa`、`v2_runtime_failure_without_expected_is_an_error_before_running_solution`、`rc13_stress_rejects_task_change_during_run`、`rc13_stress_rejects_contest_recovery_started_during_run`。[src/stress.rs](../../src/stress.rs) の `cancellation_before_persistence_commit_preserves_the_previous_generation`。
- **未検証事項・プラットフォーム依存事項** — ロックに協調しない書き手を含む全競合は未確認。スナップショット照合は対象のディレクトリ・メタデータ・復旧状態に限る。

## 4. Contest / Stress recovery

- **対象となる操作** — CLI / TUI の Contest 修復・Refresh、Stress 反例の世代置換、更新後の読込。
- **保証する動作** — Contest 修復はメタデータだけ、サンプルだけ、または両方を入れ替える。既存の `tests` は旧メタデータの所有情報と管理対象のディレクトリ・ファイル構造を確認してから移動する。正常な旧メタデータでは同一 Contest の新旧ラベルを使い、共通ラベルでは旧表記を優先する。修復可能な旧メタデータでは取得した公式 URL との照合が必要で、旧 task ID と URL が不整合なら同じラベルも要求する。Stress は保存先のメタデータと許可されたファイルを確認する。両経路とも旧データを退避してから no-clobber で配置し、完了した復旧領域には旧データが残り得る。
- **拒否・失敗・中断時の動作** — 既存メタデータの別 Contest、所有不明、未対応バージョンや未所有の `tests` 項目を拒否する。修復確認の取消や、準備後に検出した変更でも止まる。`--force` でも所有確認を行う。異常時は可能な場合に旧データを戻す。競合で戻せない場合や完了処理に失敗した場合は復旧データを保全する。復旧が必要な Contest staging や該当問題の Stress staging は読込・再更新を止める。Stress staging の所有を特定できない場合は他の問題にも影響する。
- **保証しない範囲と例外** — サンプル本文や件数の一致だけでは所有を立証できない。移動前の Contest staging に intent も旧データもなければ、存在だけでは読込を止めない。復旧・中断アーカイブ（Contest の `.atc-recovery-*` / `.atc-aborted-*`、Stress の `.stress-recovery-*` / `.stress-aborted-*`）は、識別と完了記録の検査を通れば読込を妨げない。新データ配置後のエラーもあり、エラーが旧状態への復帰を意味する保証はない。自動復元や複数ファイル全体の原子的な切替は保証しない。
- **関連する本番実装** — [src/commands/contest.rs](../../src/commands/contest.rs) の `plan_repair`、`repair_tests_health`、[src/commands/refresh.rs](../../src/commands/refresh.rs) の `prepare_refresh`、`apply_refresh`、[src/workspace.rs](../../src/workspace.rs) の `validate_existing_contest_identity`、`existing_owned_problem_indices`、`validate_refresh_owned_tests`、`contest_recovery_state`、`complete_contest_staging`、[src/stress.rs](../../src/stress.rs) の `persist_failure_inner`、`ensure_no_interrupted_generation`、`rollback_previous_generation`。
- **関連する回帰テスト** — [src/commands/contest.rs](../../src/commands/contest.rs) の `matching_official_samples_do_not_establish_ownership_for_either_update`、`unknown_metadata_owner_cannot_offer_repair_or_change_files`。[src/commands/tests.rs](../../src/commands/tests.rs) の `prepared_refresh_rejects_destination_metadata_changes_before_apply`。[src/workspace.rs](../../src/workspace.rs) の `refresh_install_and_rollback_race_preserves_competitor_and_recovery_data`、`completed_contest_refresh_retains_previous_metadata_and_tests`、`failed_contest_completion_record_preserves_staging_and_blocks_read`。[src/stress.rs](../../src/stress.rs) の `interrupted_replacement_blocks_a_new_stress_save_without_touching_recovery`、`installed_failure_with_blocked_staging_cleanup_is_not_reported_as_saved`（Windows）。
- **未検証事項・プラットフォーム依存事項** — 停電や任意の強制終了時点での耐久性、全ファイルシステムでの復旧可否は未確認。共有違反など OS による移動の失敗もあり得る。

## 5. Watch / TUI consistency

- **対象となる操作** — Plain Watch、TUI の監視・実行キュー、Contest 切替、TUI Refresh。
- **保証する動作** — Plain Watch は起動時の設定で各バッチを同期処理する。同じ Contest の有効なメタデータをバッチごとに取り込み、Test の読込時にも現在の対応を検証する。TUI は問題と実行 ID を照合して古い結果を捨て、Contest セッション間でチャネルを分離する。Refresh は適用データを先に準備し、旧セッションの実行・監視・詳細解析ワーカーを停止して join してから、適用 → ディスクから再読込 → 新セッション開始の順に進める。
- **拒否・失敗・中断時の動作** — Plain Watch は一時的にメタデータを読めない場合も最後に確認できた対応を保持し、個別 Test の読込エラーを報告して監視を続ける。TUI は準備データと現在の Contest が異なる場合や旧セッションの停止に失敗した場合に適用を拒む。適用失敗時もディスクからの再構築を試み、成功すれば失敗表示を引き継ぐ。再読込・起動も失敗すればエラーで終了する。
- **保証しない範囲と例外** — TUI は Contest を新規に開く・切り替える際に設定・認証を読み込む。Refresh の再構築は直前の設定と同じ `SessionAuth` を使うため、外部の設定・認証ファイルを読み直す契機にはならない。HTTP 応答による認証更新は[契約 8](#8-credential-secrecy)の経路で起こる。提出ワーカーはワークスペース側が管理し、Contest セッションの停止対象から外れる。
- **関連する本番実装** — [src/commands/watch.rs](../../src/commands/watch.rs) の `watch`、`process_changed_paths_with`、[src/tui/app.rs](../../src/tui/app.rs) の `WatchApp::run_event`、`WatchApp::current_run_mut`、[src/tui/mod.rs](../../src/tui/mod.rs) の `handle_messages_with_destination`、[src/commands/watch_tui.rs](../../src/commands/watch_tui.rs) の `prepare_workspace_contest_entry`、`ContestSession::shutdown`、`rebuild_contest_session_after_refresh`、`rebuild_active_contest_session_after_refresh`。
- **関連する回帰テスト** — [src/commands/watch.rs](../../src/commands/watch.rs) の `watch_rechecks_contest_recovery_after_startup`。[src/tui/mod.rs](../../src/tui/mod.rs) の `old_session_messages_cannot_modify_a_new_session_app`、`stale_run_messages_in_the_same_drain_cannot_overwrite_a_newer_request`。[src/commands/watch_tui.rs](../../src/commands/watch_tui.rs) の `refresh_rebuild_orders_shutdown_apply_load_and_start`、`refresh_shutdown_failure_drops_prepared_data_without_applying`、`refresh_apply_failure_recovers_a_fresh_session_and_reopens_failed_modal`、`production_refresh_rebuild_preserves_the_active_contest_environment_snapshot`、`production_switch_starts_fresh_config_auth_and_workspace_routing_generations`。
- **未検証事項・プラットフォーム依存事項** — すべてのエディタの保存方式で全通知が届くかは未確認。監視パスの対応は[契約 9](#9-windows--macos-filesystem-differences)を参照。

## 6. User file preservation

- **対象となる操作** — Contest・ソース作成、Workspace 初期化、Config・テンプレート・Stress 補助ファイルの初期化、Global Settings と TUI の User Input の保存。
- **保証する動作** — Contest 新規配置はステージ済みディレクトリの no-clobber 移動、ソース作成は `create_new` を使う。初期化で既存の有効な設定やテンプレートは内容を書き換えず、欠けたファイルだけを no-clobber で配置する。Global Settings の既存ファイル保存は、読込時のバイト列・ファイルの同一性・対象属性を照合し、同じ親ディレクトリの一時ファイルから置換する。未作成の設定は no-clobber で公開する。既存の User Input の編集保存は問題単位のロック下で編集開始時の内容を照合し、差分や欠損があれば書き込まない。
- **拒否・失敗・中断時の動作** — ソース作成は同名の既存エントリを上書きしない。Workspace マーカーと Stress 補助ファイルの初期化は最終要素に `symlink_metadata` を使い、通常ファイルとして扱えない既存項目を拒否する。Contest の管理ファイルは操作ごとに通常ファイル・実ディレクトリを確認し、Windows の reparse point も検査する。Global Settings の構造化保存は末端の symlink / reparse point を拒否し、外部変更や同じ内容での差し替えを検出したら競合として扱う。
- **保証しない範囲と例外** — Global Config・テンプレートの初期化は、既存の有効なリンク先ファイルやディレクトリを許容する。壊れたリンクや種類が違う対象は拒否する。Global Settings もリンク先が通常ファイルなら閲覧できる場合がある。これらの規則は各操作の対象要素に適用される。複数ファイルの初期化や直接のソース書込に一括ロールバックはなく、Settings は置換後の同期・再検査の失敗で新しい内容が既に見える場合がある。

## 7. Submission safety

- **対象となる操作** — CLI / TUI の 1 回の提出、送信前取消、受理後の提出 ID 特定と結果追跡。
- **保証する動作** — 選んだソースを一度読んだスナップショットと task ID を使い、取得したフォームの Contest、task、言語を検証する。1 回の提出操作の物理 POST は最大 1 回。専用クライアントは POST のリダイレクト追従と再試行を無効化する。フォーム取得の GET は最終 URL を照合し、429 の上限付き再試行がある。TUI では送信開始の判定より先に取消が成立した場合は POST しない。POST 直前に認証状態と問題の対応も確認する。
- **拒否・失敗・中断時の動作** — POST のタイムアウト・接続切断・5xx や想定外のリダイレクト等は受理不明（`Unknown`）となり、自動再送しない。受理は同一 Contest の提出一覧を示す正規の 302/303 で確認する。POST の 429 はレート制限、ログインへのリダイレクトは認証要求として扱う。受理後に ID 特定・結果追跡が失敗した場合は受理済み・追跡不能（TUI の `Untracked`）として扱い、CLI は提出成功を維持する。
- **保証しない範囲と例外** — 送信開始後の取消で POST を取り消せる保証はない。同一 TUI ワークスペースの履歴では Contest ID と task ID の組ごとに開始中・ID 特定中・`Unknown` の再提出を制限する。`Untracked` は再提出を妨げない。別プロセス・別ワークスペース・再起動をまたぐ重複防止は保証しない。結果追跡は送信前後の同一 task・言語の一覧差分を使い、観測期間中の新規 ID が一意のときだけ ID を採用する。他プロセスの提出だけが見えた場合の帰属までは保証しない。
- **関連する本番実装** — [src/atcoder.rs](../../src/atcoder.rs) の `build_submit_http_client`、`HttpSource::send_authenticated_once`、[src/atcoder/submit.rs](../../src/atcoder/submit.rs) の `HttpSubmitTransport::post_submit_form`、`fetch_fresh_submit_page_until`、`classify_submit_response`、[src/commands/submit.rs](../../src/commands/submit.rs) の `execute_prepared_with_client`、`execute_prepared_with_tracking_diagnostics`、[src/atcoder/submission_tracking.rs](../../src/atcoder/submission_tracking.rs) の `discover_submission_with_transport_until_observed`、[src/tui/submission.rs](../../src/tui/submission.rs) の `SubmissionCancellation::try_begin_post`、`SubmissionHub::ensure_start_allowed`。

## 8. Credential secrecy

- **対象となる操作** — `REVEL_SESSION` の読込・保存・リセット、`atc login` / TUI の認証確認、HTTP 通信、提出診断。
- **保証する動作** — Cookie はプラットフォームの状態パスに置く。atc-rs 管理下の階層とファイルはリンクをたどらず検査し、保存は一時ファイルを書いてから置換する。Unix では新規ファイルを mode `0600` で開き、グループ・その他のアクセスビットを持つ Cookie は読込を拒否する。送信・更新受理は HTTPS の `atcoder.jp` の同一オリジンに限定する。通常の UI・エラー・診断や認証型の `Debug` に Cookie 値を出さず、送信ヘッダーを sensitive とする。
- **拒否・失敗・中断時の動作** — 欠損だけを未設定として扱い、不正な形式、非通常ファイル、管理下の危険なパスは拒否する。設定済みセッションではスコープが適合する `Set-Cookie` を応答の順に評価し、最後の有効な更新・削除を採用する。認証確認も同じ通信経路を通るため、`atc login` の結果とは別に保存 Cookie が更新・削除され得る。自動永続化はロック下で現在の保存値を照合し、外部の別の値や削除を検出したら上書き・再作成しない。実行中の認証状態にはサーバー側の変更が残り、保存失敗は秘匿された警告になる。
- **保証しない範囲と例外** — 状態ディレクトリのプラットフォーム基点には OS によるリダイレクトを許す。自動更新の値照合で同じ値への差し替えは区別できない。`ATC_SUBMISSION_TRACE_RAW` を有効にすると、追跡用 GET の応答本文（提出前一覧・ID 探索・判定状況）を加工せず、1 試行の合計上限まで保存する。通常の診断は構造化された記録を扱う。raw 本文はログイン中の私的データやトークンを含み得るため秘匿の対象外で、共有・コミット用の資料として扱えない。
- **関連する本番実装** — [src/paths.rs](../../src/paths.rs) の `cookie_location`、[src/auth.rs](../../src/auth.rs) の `open_state_directory`、`replace_cookie_file`、`SessionAuth::cookie_header`、`SessionAuth::observe_trusted_set_cookie_batch`、`SessionAuth::persist_pending`、`AuthStore::mutate_if_current`、[src/atcoder.rs](../../src/atcoder.rs) の `authentication_status`、`HttpSource::exchange_with_warning_sink`、`SessionCookieProvider::cookies`、`SessionCookieProvider::set_cookies`、[src/tui/authentication_modal.rs](../../src/tui/authentication_modal.rs) の `render_secret_input`、[src/atcoder/submission_diagnostics.rs](../../src/atcoder/submission_diagnostics.rs) の `AttemptDiagnostics::from_env`、`AttemptDiagnostics::capture_raw`。

## 9. Windows / macOS filesystem differences

- **対象となる操作** — no-clobber 移動、Global Settings の既存ファイル置換、サンプルの所有確認、Watch のパス対応。
- **保証する動作** — no-clobber 移動は Windows で `MoveFileExW`（置換フラグなし）、macOS で `renamex_np`（`RENAME_EXCL`）を使う。Windows の既存 Settings は `ReplaceFileW` に属性・ACL の引継ぎを委ね、保護対象の属性ビット（Hidden、Read-only、System）を比較する。macOS では一時ファイルへメタデータをコピーし、mode・ACL・xattr が読込時の契約と一致するかを置換前後に検査する。macOS の Watch は監視登録先だけを canonicalize し、通知パスの該当プレフィックスを元のルートに戻してから、共通のソース対応でパスを照合する。
- **拒否・失敗・中断時の動作** — 移動の衝突、Windows の共有違反、macOS の属性の読込・コピー失敗や外部変更を検出したときはエラーにする。macOS では置換後に親ディレクトリを同期し、そこで失敗すれば新内容が残り得る。サンプル所有確認は大小文字違いのパスが同一ディレクトリを開けた場合に限って別表記を認める。別ディレクトリなら、表記が似ているだけで所有対象に含めない。
- **保証しない範囲と例外** — 大小文字の区別は実際のファイルシステムと対象ディレクトリに依存する。Watch の変換は監視ルート配下の通知を元の表記に戻す処理で、任意の別名の統合は行わない。Windows では Unix 相当の親ディレクトリ同期を実施しない。Settings のメタデータ契約を他のファイル置換に適用しない。
