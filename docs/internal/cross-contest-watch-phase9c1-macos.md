# Cross-Contest Watch Phase 9C-1 macOS 最終回帰確認

2026-11-27。Phase 9B の `40ac947` と、今回の RSS 回帰修正を適用した作業ツリーを検証した。差分の起点は Phase 9A 報告を収めた `cbdb339`、リリース実行ファイルの比較元は Phase 9A が検証した `1fa0982`。macOS 26.6.2（25G83）、Apple M2（8 コア、メモリ 16 GB）、大小文字を区別しないローカル APFS、Rust 1.97.1、Python 3.14.6、notify 9.0.0、notify-types 2.3.1 で確認した。[Phase 9A macOS](cross-contest-watch-phase9a-macos.md)・[Phase 9B Windows](cross-contest-watch-phase9b-windows.md)・[OS 別検証手順](cross-contest-watch-validation.md)

**判定はリリース準備へ進行可。** Phase 9B の読み込み上限と macOS の監視継続・復旧を確認した。追加で見つかった上限内の RSS 回帰を修正し、通常リリース版と全回帰で再確認した。今回の共通コード修正を反映した Windows 実機の再検証は公開前の残件。

## Phase 9B の変更と macOS への影響

- Workspace 診断と `ContestTaskSnapshot` の再読込は同じ `MAX_CONTEST_METADATA_BYTES`（16,777,216 バイト）を使う。開いた通常ファイルの属性で上限超過を拒否し、読み込み開始後の増加にも上限と超過判定用の 1 バイトを適用する。スナップショットのファイル実体・バイト列とポーリング用の属性は同じハンドルから取得する。macOS の no-follow とデバイス・inode によるファイル／ディレクトリの実体照合、Recovery 状態、配置ルールと Contest ID の所有権検証は維持されている。[共通読み込み](../../src/safe_file.rs)・[診断](../../src/workspace/diagnosis.rs)・[スナップショット](../../src/workspace.rs)
- 監視中の配置・マニフェスト再照合で一致しなくなった対象は、その世代だけを失効する。保存通知を現在の所有経路・登録世代と照合し、物理 attempt の直前にも再検証する。対象の実行を中断・join してキューと結果を取り除き、復元時には新しい世代を登録する。FSEvents の登録と通知集約、Windows の reparse point 検査とファイル識別は既存の経路を通る。[監視と世代失効](../../src/commands/workspace_watch.rs)・[実行前検証](../../src/commands/attempt_executor.rs)・[macOS の登録](../../src/watcher/macos_workspace.rs)

### 上限内のマニフェストで見つかった RSS 回帰

Phase 9B は上限超過の 64 MiB 置換を早期に拒否した。一方、上限内の有効な 16 MiB の TOML を持つ Contest で、保存・自動切り替え時のピーク RSS が Phase 9A より増えた。計測版では 16 MiB を読み切ったバッファの容量が毎回 32 MiB となり、再照合、保存受付、物理実行、表示準備で大きな読み込みが繰り返された。

上限以下と確認済みのファイルサイズを使って、読み込み前に必要な容量を予約するよう共通処理を修正した。上限超過の早期拒否、読み込み中に増加したときの 1 バイト分の超過判定、同一ハンドルからの実体と属性の取得は維持する。境界の既存テストに、上限内の通常ファイルでバッファ容量が内容の 2 倍に達しないことを追加した。[読み込みの修正](../../src/safe_file.rs)・[境界の回帰テスト](../../src/workspace.rs)

通常リリース版で、非表示 Contest のマニフェストを有効な 16 MiB の TOML に置換して 2.5 秒待ち、対象のソースを保存して自動切り替えと `1/1 AC` を確認した。コメント 1 行と短いコメントの繰り返しの 2 種をビルドごとに各 3 回実施した。単位は MiB。

| --- | --- | ---: | ---: | ---: |
| コメント 1 行 | 再照合時の最大観測 RSS | 49.59–49.73 | 67.61–67.84 | 47.45–47.56 |
| コメント 1 行 | プロセス生存期間の最大 RSS | 81.95–82.19 | 181.12–292.28 | 79.88–79.92 |

16 MiB の直前・同値・1 バイト超過へ連続して置換し、各段階で保存する境界試験でも各ビルド 3 回測定した。プロセス生存期間の最大 RSS は Phase 9A で 140.45–140.50 MiB、Phase 9B で 192.33–528.78 MiB、Phase 9C-1 で 104.03–104.11 MiB。境界での受付・拒否は全試行で一致した。

| 読み込み中の増加 | 実ファイルを開き、属性取得後の最初の読み取りを終えた時点で別ハンドルから追記する既存テストが成功した。縮小した上限 16 バイトで検証し、`InvalidData`、読取位置 17 バイト、ファイルの最終サイズ 40 バイトを確認した。TUI のタイミングには依存せず、共通の読み込み本体をテストした。[読み込みの回帰テスト](../../src/safe_file.rs) |

## リリース TUI の既存動作

| 確認項目 | macOS で観測した結果 |
| --- | --- |
| 通常保存・Atomic Save・自動切り替え | 上書き、同一内容の再保存、Atomic Save、削除後の再作成でテストが走り、Cross-Contest Watch ON で保存先を表示した。chmod のみでは実行も表示切り替えもなかった。別 Contest の連続保存では後の保存先を先に実行・表示し、先の保存先も非表示のまま実行した。 |
| 手動切り替えと結果保持 | ON で非表示 Contest に戻ると、完了済みの `1/1 AC` を表示した。切り替えモーダル中は非表示 Contest のテストを継続し、手動確定で先行する自動切り替え候補を無効にした。別 Contest の保存による Sample Test の先取りと再キューを、子プロセスの起動順「元 → 新 → 元」で確認した。 |
| Refresh・Migrate | TUI Refresh は欠けたサンプルを修復し、その後のソース保存で `3/3 AC`。外部 CLI Migrate で独自ファイルがバックアップに残り、稼働中の TUI は移行後の保存を受け付けて `3/3 AC`。いずれもローカルの AtCoder fixture を使用した。 |

### Contest 追加直後の保存

Phase 9A の PTY と単調時刻の計測方法を再利用した。`40ac947` と RSS 回帰修正後の作業ツリーのコピーに時刻記録と書き込み点を加え、通常リリース版とは別にビルドした。500 Contest の稼働中に配置ルールの更新で 180 Contest を追加し、対象 1 件の正規ソースを監視スレッドから書き換えた。対象の基準指紋採取、FSEvents の論理登録更新、更新後の照合、コールバック、RunScheduler の受付、Python 起動、TUI 表示を記録した。各条件・各ビルド 3 試行。表は RSS 回帰修正後の 1 試行あたりの件数。

| 保存時点 | 通常通知の受付 | 照合による回収 | 実行 | 自動切り替え |
| --- | ---: | ---: | ---: | --- |
| 初回の基準指紋を取得する直前 | 0 | 0 | 0 | なし |
| 基準指紋の取得直後 | 1 | 0 | 1 | あり |
| 監視の関心パス公開後、FSEvents の一括登録更新を呼ぶ直前 | 1 | 0 | 1 | あり |
| FSEvents の一括登録更新完了の直後 | 1 | 0 | 1 | あり |
| 登録後の再照合で対象ソースを読む直前 | 0 | 1 | 1 | なし |
| 登録後の再照合完了の直後 | 1 | 0 | 1 | あり |

修正後は、初回指紋取得完了から論理登録完了まで 9.3〜11.8 ms。対象パスへの FSEvents コールバックは各試行で 2 件ずつ届いた。同一ボリュームの親を既に監視しているため、対象の論理登録前に書き込んだ場合も、更新後に通常通知として受け付けることがある。基準指紋の取得直後に書き込んだ Phase 9B の 3 試行では回収で各 1 回実行し、画面を維持した。両ビルドとも初回指紋取得後の 15 試行で各 1 回実行し、取得前の 3 試行は変更を基準に取り込んだ。Phase 9A の単発の未受付は当時の取得・登録時刻が不明で、原因は未確定のまま。[Phase 9A の連続動作試験](cross-contest-watch-phase9a-macos.md#連続動作)・[macOS の監視登録](../../src/watcher/macos_workspace.rs)

## 文書と既知の制約

- Phase 9B が修正した ARCHITECTURE と INVARIANTS は実装に一致する。ON の通常切り替えは画面の購読を終了し、実行世代・キュー・結果を保持する。単一 Contest モードの切り替え、Home 復帰、対象の Refresh はそれぞれのライフサイクルで旧世代を失効させる。INVARIANTS の診断・再照合の 16 MiB 上限と、超過時の対象世代失効も確認した。[ARCHITECTURE](ARCHITECTURE.md#plain-watch-と-tui-watch)・[INVARIANTS](INVARIANTS.md#5-watch--tui-consistency)・[TUI ライフサイクル](../../src/commands/watch_tui.rs)
- 新規対象の初回指紋取得より前の変更は比較の基準に取り込まれる。回収は確認時に残っている差分を対象とし、欠落した中間状態・保存順序は復元できない。自然発生した OS 通知の飽和、Linux 実機、数時間以上の連続運転は未検証。
- Source Snapshot は未導入で、実行時は検証した現行パスからソースを読む。手動 Open の準備には健全性確認後の表示用読み込み `load_metadata_unchecked` があり、その間の差し替えに対する上限は今回の確認範囲外。実 AtCoder への通信・提出は行っていない。[Source Snapshot の調査](local-source-execution-study.md)・[画面準備](../../src/commands/watch_tui.rs)・[表示用の読み込み](../../src/workspace.rs)
- Windows の大規模 Workspace の起動時間は Phase 9B の測定範囲に限る。1,000 Contest の再測定で Phase 9B の初回 Open の中央値は新規データで約 4.08 秒、ウォームで約 1.32 秒。今回の共通読み込みの修正を適用した Windows 実機の再検証は未実施。[Phase 9B の最終性能測定](cross-contest-watch-phase9b-windows.md#最終性能測定)
