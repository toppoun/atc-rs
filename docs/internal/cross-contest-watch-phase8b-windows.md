2026-11-26、`2062286` を Windows 11 25H2（26200.9974、x86_64）で検証した。通常ユーザーの Medium Integrity、Ryzen 7 9800X3D（16 論理 CPU）、使用可能な物理メモリ 31.1 GiB、大小文字を区別しない NTFS、Rust 1.97.1。Windows は notify 8.2.0、macOS は 9.0.0 を使い、両者の `notify-types` は 2.3.1。

## クリティカルパス

一時コピーのリリースビルドで、ウォーム各条件3回と1,000 Contest の初回アクセス各条件3回を測った。Inclusive はそのスコープ全体、Exclusive は同一スレッドの計測子スコープを除いた値。別スレッドの UI 待ちと監視初期化は同時刻に進むため、両方を足さない。囲ったスコープを観測した値で、子スコープを置いていない処理は Exclusive に残る。各行の中央値は独立に算出した。

Home は Enter で表示対象を再解決してから準備スレッドを起動する。既存 Contest の診断後に、対象のサンプル、Stress、User Input を読み込む。Home が準備結果を受け取ると、ルートをもう一度照合してセッションを作る。ON の初回は RunWorker を起動し、監視スレッドの Ready を待つ。監視スレッドは Workspace 探索、Contest 診断、実行世代とソース索引の登録、基準指紋取得、notify 登録を行い、登録後に指紋を同期照合する。Ready 後に表示対象の現行の所有権・マニフェスト・実体を照合して登録に接続し、WatchApp を生成して描画する。Home と Contest のイベントループには 20 ms のポーリング区間がある。

同じ1,000件・同じ計測点の初回アクセスでは Enter → 描画後が 4,463.73 ms、配置・登録準備が 3,824.44 ms、うち基準指紋が 1,823.36 ms、所有権・サンプル診断が 1,364.33 ms。すでにファイルにアクセスした後の登録後指紋照合は 564.45 ms だった。ウォームとの差は no-follow オープンで約2,440 ms、列挙の開始で約118 ms、属性取得で約125 ms、本文読み込みとハッシュで約42 ms。オープン回数は同じで、初回アクセスに依存する待ち時間が支配的だった。NTFS のキャッシュ、ストレージ、ファイルシステムフィルターそれぞれの寄与は未分離。SHA-256 の置換や、notify 登録だけの改善でこの差を説明できる測定結果は得られていない。

### 再利用できる範囲

- 登録前と登録直後の指紋取得は別の観測で、その間に通知を受け取れなかった保存を見つける。共通化するなら実行した検査やハンドルの寿命を整理する。基準の指紋を登録後の観測に流用すると回収の意味が変わる。[`WatchIndex::initialize`](../../src/commands/workspace_watch.rs)
- 1候補ごとに親を開き、実体照合、通常ファイルの存在確認、存在時は正確な名前を列挙で検証する。NTFS が異なるケース表記を受け入れても索引の正規名だけを対象にする。候補が4件ある場合、隣接する候補間で親ハンドルを再利用する余地はある。ファイルが置換される競合には、読み込み前後の属性・実体、同じ名前を開き直す照合が必要。[`open_watched_source_parent`](../../src/workspace.rs)、[`read_stable_regular_file_at`](../../src/safe_file.rs)
- 同じ Contest の起動診断と `RunContext` の構築では、マニフェストを複数回開き、Recovery を確認する。探索で得た実体、診断したバイト列、実行への固定、表示への接続、物理実行直前の検証は異なる境界。連続した同一境界で開いたディレクトリと検証済みの内容を引き渡せる箇所を調べ、次の境界では新たに照合する。[`diagnose_watch_contest`](../../src/workspace/diagnosis.rs)、[`RunContext`](../../src/commands/attempt_executor.rs)、[`ContestTaskSnapshot`](../../src/workspace.rs)
- 表示対象は確定の再解決と準備の両方で表示データを読む。モーダル確定時に破棄されるデータのロードを準備側にまとめる余地がある。対象の健全性と最終経路照合は維持する。削減対象の規模は合成条件で数 ms。[`resolve_contest_open`](../../src/commands/watch_tui.rs)

## 試作の比較

どちらも一時コピーのリリースビルドで、計測スパンを無効にし、同一ウォーム Workspace で基準と試作の順番を交互にした7組。表は Open の中央値、その後に各組の「基準 − 試作」の中央値と範囲を示す。試作ごとの値は同じバイナリ内の比較。

| 試作 | Contest | 基準 → 試作 (ms) | 組ごとの差 (ms) |
| --- | ---: | ---: | ---: |
| A の一部。開いた CapDir のハンドルを借用し、複製を省く。同じ Win32 実体取得を行う | 500 | 795.5 → 773.7 | +10.7 [−93.7～+73.2] |
| 同上 | 1,000 | 1,491.0 → 1,500.3 | −17.4 [−301.7～+166.5] |
| B の一部。基準指紋だけで親ハンドルを最大4候補で共有。各候補の正確な名前とファイル本体の確認を維持 | 500 | 793.3 → 799.3 | +23.0 [−50.6～+34.9] |
| 同上 | 1,000 | 1,462.6 → 1,427.4 | +35.2 [+15.5～+284.8] |

A の試作はハンドル複製と解放に限り、改善を分離できるほどの差は出なかった。B の試作は1,000件の全組で速く、差の中央値は35 ms。再 Open は1,486.4 → 1,447.3 ms、組ごとの差は +45.9 ms［−158.0～+82.0］。基準指紋の共有を試した範囲で、Ready 後の照合は計測対象外。

合成 NTFS ディレクトリを Win32 で開くと、安全な Contest オープンと同じ共有モードでは開いたディレクトリの直接移動が共有違反32、祖先の移動がアクセス拒否5で失敗した。監視側と同様に `FILE_SHARE_DELETE` を加えた状態では直接移動が通り、祖先の移動は拒否された。両モードで直下の通常ファイルの外部置換は成功した。閉じた後は両方の移動が通り、junction を no-follow で開いて reparse 属性を取得できた。実装時には共有時間の上限を決め、ファイル置換・親経路の変更が同時に起きる操作で再確認の境界を検証する。

## 改善案と実装順

| 案 | 実測から分かる対象と設計上の条件 | 優先度 |
| --- | --- | --- |
| A　重複 I/O と検証の削減 | 診断・登録準備、基準指紋、定期照合を改善できる。ひと続きの処理内だけで同じ開いた実体を使い、パスの再確認が必要な境界にデータを持ち込む場合は新たに照合する。診断済みバイト列・パース結果の引き渡しと、表示で破棄される二重ロードを優先する。 | 最初 |
| B　Contest 単位のハンドル共有 | コンテキスト登録や正規ソース確認で親の再オープンを減らせる。Windows の安全な Contest オープンは `FILE_SHARE_READ \| FILE_SHARE_WRITE` を使用し、notify の監視ハンドルとは共有モードが異なる。長く保持すると Contest の移動に干渉する。候補数と時間を上限とし、境界で手放す。列挙結果は作業単位内の候補の絞り込みに使い、ファイルを開く時点の名前・実体・reparse の保証を別に確かめる。 | A の後に個別比較 |
| C　実行コンテキストの遅延初期化 | 1,000件で約265 ms の RunContext 構築が対象。索引に必要な task、実体、配置、登録世代と、実行の直前に必要な情報を分ける。診断時の実行世代と現行マニフェストの不一致は遅延後も拒否する。初回保存の体感時間と、Refresh/Migrate 中に遅延初期化を競合させたときの旧世代拒否を確認する。 | A の結果次第 |
| D　初期指紋照合の分割・遅延 | Windows の初期照合は現在も Phase 8A と同じ処理単位で回すが、Ready 前に全単位を同期で完了する。後段へ移せる理論上の区間はウォーム約432 ms、初回アクセス約564 ms。移す場合は登録前後の保存の回収、Ready 直後の通常通知との重複排除、手動操作と自動切り替えを許す範囲を定義する。 | Ready を維持する改善を先に評価 |
| E　限定並列 I/O | 初回アクセスのファイルオープン待ちの一部を重ねられる可能性。安全な読み取りだけを少数の並列度で試し、結果は単一の監視スレッドで世代・所有権を確認して順に反映する。キャンセル、join、開くハンドルのピーク、本番保存時の待ち時間を比較する。 | 初回オープン待ちが残る場合 |
| F　バックグラウンド初期化 | 表示を先にできる一方、他 Contest の監視・回収と自動切り替えが利用可能になる時点が分かれる。起動中の Home 復帰、終了、更新競合も新たに扱う。 | A～E で不足する場合に再評価 |

まず共通の診断と索引構築で検証済み情報の寿命を限定し、重複する読み込みを減らす。Windows・macOS の同じ安全性テストで競合時の拒否を確認し、4規模の初回アクセスとウォームを同じ手順で再測定する。次に Windows の短いハンドル共有を単独で測り、reparse point・同一名への外部置換・親と祖先の移動・停止時のハンドル解放を検証する。そこまでの改善幅を見て C と D を別々に比較する。

macOS でも A は索引、基準指紋、配置・マニフェスト診断、定期照合の総作業量に効く可能性がある。B の共有モードに由来する効果は Windows で測った結果に限る。macOS は FSEvents の一括登録を維持し、登録集合・世代が同じ場合は更新を省く。Ready 後に回収する macOS の初期照合と、Windows の Ready 前の初期照合は、各 OS で登録前後の保存を試す。定期照合の改善は総処理時間と手動切り替えの遅延の両方で判断する。

単一 Watcher・RunWorker・RunScheduler、物理 attempt 最大1件、実行世代と所有権、通常通知の受付順、固定150 ms、通知欠落からの回収と重複排除、回収イベントで自動切り替えしないこと、Cancellation / Join、OFF・Standalone・Plain Watch と結果保持を設計条件とする。ソース本文の保存や永続的な索引を導入する設計は [Phase 7C の調査記録](local-source-execution-study.md) を参照。
